- **An image can set the user an exec without `user` runs as (#595).** The daemon reads
  `AGENTD_DEFAULT_USER` from the image's environment at startup: a user name, or a uid as
  digits. A start request that omits `user`, from `exec` or `run --exec` alike, resolves it at
  each start to a row of the guest's `/etc/passwd`, by name or by uid, so a user an earlier exec
  created resolves on the next. The child gets that row's uid, primary gid, `HOME`, `USER` and
  `LOGNAME`, a uid included. A request's own `user` still runs as given, `root` and `0`
  included. If no row matches, digits included, each start without a `user` answers
  `400 unknown_user`, and the detail mentions the variable. Uploads follow the same row: what
  `PUT /v1/fs/tar` and `PUT /v1/fs/file` create, parent directories included, belongs to the
  default user, so a nameless exec can write the tree `run . --exec` and `cp` upload, and what
  already existed keeps its owner. A default with no row refuses an upload with the same
  `400 unknown_user` before anything is written. With the variable unset, nothing changes.
  Workload hook handlers still run as root. The agent recipe's `chown` of `/workspace` and a
  sync's in-guest deletions now ask for uid 0 by number, so an image's default user can't make
  them fail. An image that sets the variable needs a client at this release or later: an older
  client sends that `chown` and those deletions with no `user`, so they run as the default user
  and fail.
